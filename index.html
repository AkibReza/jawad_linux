01. Project Foundation

Project Overview & Objectives

Confidentiality

Encrypts files using standard AES-256-CBC. Employs PBKDF2 with 100,000 iterations and salt, rendering brute-force and rainbow-table attacks computationally infeasible.

Atomic Directory Support

Solves the classic limitation where tools only encrypt single files. Seamlessly bundles entire directory hierarchies with tar+gzip before encryption, restoring them automatically on decrypt.

Integrity & Accountability

Computes SHA-256 cryptographic hashes to detect file tampering or corruption. Maintains a timestamped audit trail (vault_audit.log) of all operations.

03. System Architecture

How The Script Operates Under The Hood

1 Encryption Pipeline

File or Directory
Step A Input validation: Verify target exists (-f or -d).
Step B If Directory: Archive to temp tarball via tar -czf.
Step C Masked password prompt (read -s) with double confirmation.
Step D Compute plain SHA-256 checksum for audit & integrity.
Step E openssl enc -aes-256-cbc -salt -pbkdf2 -iter 100000
Step F Log to vault_audit.log & optional secure shred (shred/dd).

2 Decryption & Auto-Detection Pipeline

Smart Extraction
Step A Read *.vault package; create secure isolated temp file.
Step B Prompt for password; execute openssl enc -d via stdin.
Step C Verify return code $? (reject wrong password cleanly).
Step D Magic Auto-Detect: Run tar -tzf $temp.
Step E If archive: extract tree. If single file: restore file.
Step F Compute restored SHA-256 and confirm integrity match.

Key Faculty Talking Point: Signal Handling with trap

If a user hits Ctrl+C or sends a SIGTERM, the script catches it via trap cleanup EXIT INT TERM, overwriting temporary files with random bytes from /dev/urandom before deleting them.

Function: encrypt_directory() vault.sh lines 205-265 
# 1. Create temporary tar archive
local temp_tar
temp_tar=$(mktemp "/tmp/vault_dir_XXXXXX.tar.gz" 2>/dev/null || mktemp "./.vault_dir_XXXXXX.tar.gz")
TEMP_FILES+=("$temp_tar")

# 2. Bundle folder contents into archive preserving hierarchy
tar -czf "$temp_tar" -C "$(dirname "$indir")" "$(basename "$indir")" 2>/dev/null

# 3. Encrypt archive with AES-256-CBC and PBKDF2 (100,000 iterations)
printf "%s" "$password" | openssl enc -aes-256-cbc -salt -pbkdf2 -iter 100000 \
    -in "$temp_tar" -out "$outfile" -pass stdin 2>/dev/null
What to say to faculty:

"Standard online scripts fail when you pass a directory to OpenSSL because ciphers operate on byte streams, not filesystem hierarchies. Here, I use UNIX composition: tar -czf serializes the folder structure into an archive, which is then encrypted atomically."

06. Viva Voce Masterclass

Top 10 Faculty Viva Questions & Answers

Memorize these concise, accurate answers before your lab examination or project presentation.

Q1

Why did you use OpenSSL instead of writing encryption directly in Bash?

Answer: Bash is an operating system command orchestration language (glue language), not designed for low-level bitwise manipulation. Writing cryptographic ciphers directly in shell would be insecure, susceptible to timing attacks, and orders of magnitude slower. Using OpenSSL leverages audited, hardware-accelerated (AES-NI) C libraries following the Unix philosophy: using the right tool for the job.

Q2

What is PBKDF2 and why did you specify 100,000 iterations?

Answer: Passwords entered by humans have low entropy. PBKDF2 (Password-Based Key Derivation Function 2) runs HMAC-SHA256 in a loop 100,000 times combined with a random cryptographic salt. This deliberate computational cost makes offline dictionary and brute-force GPU attacks computationally prohibitive without noticeably slowing down legitimate users.

Q3

Why is CBC mode preferred over ECB mode in AES?

Answer: In ECB (Electronic Codebook) mode, identical 16-byte plaintext blocks produce identical ciphertext blocks, leaking structural patterns (like the infamous ECB Penguin). CBC (Cipher Block Chaining) XORs each plaintext block with the previous ciphertext block (using a random IV for the first block), ensuring completely randomized ciphertext even for repeated patterns.

Q4

How does the script know whether a .vault file is a directory or a file?

Answer: On decryption, the payload is initially extracted to a temporary file. The script then executes tar -tzf $temp_decrypted. If tar successfully reads a gzip-compressed archive header (exit code 0), the script knows it is an archived folder and unpacks it. If it fails (exit code non-zero), it treats it as a standard file.

Q5

Why pass the password via stdin instead of -pass pass:$password?

Answer: When arguments are passed on the CLI, any other logged-in user on a shared Linux machine can see them in plaintext by inspecting the process table with ps aux or reading /proc/[pid]/cmdline. By streaming the password directly through stdin using a pipe, the secret never touches the process arguments.

Q6

What does the trap command accomplish in your script?

Answer: trap cleanup EXIT INT TERM registers an asynchronous signal handler. If the script is abruptly killed or the user presses Ctrl+C while an unencrypted temporary archive exists, the cleanup() function runs automatically, overwriting temporary files with random bytes from /dev/urandom and removing them.

Q7

What is the purpose of set -o pipefail at line 14?

Answer: By default in Bash, the exit status of a pipeline (e.g. cmd1 | cmd2) is determined solely by the last command (cmd2). If cmd1 fails, the script might still report success! Setting pipefail ensures that if any command in a pipe fails, the overall pipeline returns a non-zero exit code.

Q8

How does SecureVault prevent accidental data overwrite?

Answer: Before writing any output file (either during encryption or decryption), the script performs an existence test ([[ -f "$outfile" ]] or [[ -d "$restored_name" ]]). If the target exists, it prompts the user with an explicit confirmation dialog or automatically timestamps an alternate destination.

Q9

What does the secure shred option do?

Answer: Standard deletion via rm only unlinks the file inode from the directory table; the actual data blocks remain on disk until overwritten. SecureVault uses shred -u -z -n 3 (or dd if=/dev/urandom as a portable fallback) to overwrite the physical disk blocks with random noise before unlinking.

Q10

Why did you use getopts alongside the interactive menu?

Answer: Providing both models makes the tool flexible: interactive menu mode is accessible for casual users, while command-line options (-e, -d, -v, -l, -t parsed cleanly with POSIX getopts) allow the script to be integrated into automated backup crontabs or CI/CD pipelines.
